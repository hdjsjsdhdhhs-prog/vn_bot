# Development Workflow

## Branch policy

`main` is the production branch. Do not develop or commit directly on it.

```text
feature/fix/chore branch
        ↓
Pull Request targeting main
        ↓
Required CI checks
        ↓
Review and approval
        ↓
Merge
        ↓
Release tag and production deployment when approved
```

Use short descriptive branch names such as `feature/payment-retry`, `fix/subserver-cache`, or `chore/ai-development-setup`. Start from the latest `main` and keep the branch focused on one outcome.

A GitHub ruleset should protect `main` with Pull Requests, required checks, review approval, resolved conversations, and blocked force pushes/deletions. The repository currently reports `main` as unprotected, so an administrator must enable this in GitHub repository settings.

## Before implementation

1. Read `AGENTS.md` and the relevant documents under `doc/`.
2. Inspect the current `main`, recent commits, open PRs, and existing implementation.
3. Locate tests, migrations, configuration, Docker, and deployment impact.
4. Write a short plan. For architecture changes or more than five files, obtain approval before writing.
5. Create a dedicated branch from current `main`.

Do not create parallel modules or documentation when an appropriate location already exists. Preserve backwards compatibility unless a breaking change is explicitly approved.

## Implementation

- Keep presentation, business logic, persistence, integrations, and runtime wiring in their existing layers.
- Use Conventional Commits without generated/co-author footers.
- Do not commit secrets, production data, databases, logs, binaries, or local AI-tool state.
- Add tests with behaviour changes. Update `.env.example` for configuration changes.
- Add numbered SQL migrations for schema changes; never mutate released migrations.
- Keep documentation and VPS instructions synchronized with the code.

## Validation

Minimum checks for Go changes:

```bash
gofmt -l $(find . -type f -name '*.go' -not -path './.git/*')
go test -race -count=1 -timeout 5m ./...
go vet ./...
go build ./...
golangci-lint run ./...
```

For security-sensitive or release changes also run:

```bash
gosec ./...
docker compose config
docker compose -f docker-compose.local.yml config
docker build -t vn_bot:verify .
```

Run focused tests first while iterating, then the full suite. Do not claim a check passed unless it was actually run successfully.

## Pull Request requirements

Every PR must include:

- purpose and scope;
- changed files or components;
- exact test commands and results;
- database/configuration/deployment notes;
- security and compatibility risks;
- rollback considerations.

Keep application changes separate from unrelated refactoring. Never merge a PR merely because it was generated by an AI agent.

## Autonomous agent workflow

Notion Agent coordinates the task and records user intent. GitHub is the source of truth for code and repository state. The VPS AI Engineer may validate deployment only with explicit authorization and a reversible rollout plan.

1. Analyze before modifying.
2. Present a plan when required.
3. Work only on a dedicated branch.
4. Make the smallest coherent change.
5. Validate locally/CI without inventing commands.
6. Inspect the final diff for secrets and unrelated edits.
7. Commit and open a PR; do not push directly to `main`.
8. Do not merge or deploy without explicit approval.
9. For VPS work, back up state first and report every command and outcome.

If access, requirements, test results, migration safety, or deployment state is uncertain, stop and request clarification instead of guessing.
